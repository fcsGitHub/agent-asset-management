CHAPTER 01先看结论：一个工作台，管理能追溯的团队资产

打开项目，继续一个 Session。让 Agent 帮你查资产、整理需求、提出修改；在右侧工作区看内容、差异和证据。管理员审核具体版本后，团队才能把它当作正式资产使用。

本方案暂称 工作集（Team Asset Workspace）。目标是供小型研发团队使用的资产协同软件，不是固定资产盘点，也不是再做一个聊天客户端。需要管理的是文档、源码、模型、引擎、测试、Agent、场景，以及它们之间的关系、版本和项目交付记录。

建议采用 模块化单体业务系统 + PostgreSQL + 文件内容库 + Pi Agent 运行器。Semantica 作为可替换的语义处理组件，帮助提取实体、识别关系、整理证据。它不直接决定某个版本能否发布。界面保留 Agent 区和工作区，项目与 Session 放在可收起的导航抽屉中。

这份文档规定产品行为、数据约束、接口和验收方法。文中页面为交互示意，架构、数据表、接口均为拟建方案；没有把设计图当成已完成的软件。性能数字是待验证的目标，开源能力来自列出的官方仓库和文档。

四个容易做错的地方

容易采用的做法 本方案的决定 实际收益
文档库、模型库、软件库各建一套互不关联的数据 统一资产身份，分类视图，按类型校验属性 能查出“哪些项目在用这个模型，哪些测试证明它可用”
把最新文件覆盖旧文件 不可变修订 + 分支头 + 发布记录 历史项目和测试仍能找到当时使用的内容
Agent 说审核通过就直接发布 服务端校验，真实管理员审批，审批绑定内容摘要 提交后偷偷替换文件不会沿用旧批准
整合若干平台，用户在多个后台间切换 统一工作台，只通过适配器复用能力 保持小团队需要的简单操作

CHAPTER 02范围、默认假设与不做的事

第一版必须真的走通“上传、关联、提案、审核、复用、交付”，不能只做一个漂亮的聊天页面。

明确采用的产品规则

项目 本方案的默认规则
团队规模 首个部署以 5 至 30 名成员为设计假设；数据结构从开始就保留 team_id，不承诺无限规模
部署 浏览器访问、自托管优先；Linux 服务端，开发兼容 WSL；离线为受支持的部署配置，桌面壳后置
登录 账号登录后直接使用；不要求成员手填项目 ID、Bearer Token 或数据库连接信息
资产共享 普通正式资产团队可读；项目私有草稿只给作者、受邀协作者和审批者；确有保密需求才增加限制级别
管理员审核 资产正式变更、正式发布、候选版向指定用户群发布、本体定义与执行插件的启用，均需管理员审核
日常协作 创建 Issue、讨论、更新自己负责的任务可直接保存；不把每次发言都变成审批单
语言与模型 界面以中文为主；LLM 可配置，模型调用协议通过适配器校验，不写死供应商
数据用途 优先管理已有资产和研发过程；执行仿真、运行软件、部署 Agent 是受控扩展，绝不因文件入库就自动运行

必须完成的基础范围：七类指定资产；类型与关系定义；项目 → Session；文件上传与预览；精确版本引用；Issue、分支、PR、变更说明和管理员发布；任务与需求追踪；真实 Agent 调用；本体候选提取；权限、审计、备份恢复。

保留扩展点，但不作为第一版前提：多组织计费、公开插件商城、复杂矩阵权限、多人同字编辑、完整 Git 托管、信号级仿真、云原生微服务集群、自动写入生产环境、永久运行的多 Agent 群。

项目管理并非要求每个任务都跑齐所有流程。小修复可以采用轻量变更流程，但必须说明属于哪个交付目标、改了什么、怎样验证、由谁批准发布。跳过某个阶段必须有事先定义的模板或审批记录，不能由模型临时省略。

CHAPTER 03开源调研：复用机制，不拼接一堆后台

没有一个项目同时满足简洁工作台、异构资产本体、受控版本发布和项目全过程。推荐自建薄业务层，复用成熟基础组件。

已核实的参考方向

下表的“怎么用”是本方案的设计判断，不表示上游已经提供完整的本产品能力。未运行这些项目的整套部署与性能测试。实施时需记录所选 tag/commit、许可证、依赖、平台支持和契约测试结果，不能用仓库首页的宣传指标代替验证。

项目 / 来源 值得借鉴或复用的部分 本项目如何使用 不直接照搬的原因
Kimi Code Desktop / Kimi Code [1][2] 工作空间、会话、对话发起操作、审批和结果查看 参考信息布局与操作顺序 官方产品可作交互参考，不等于其桌面实现可任意作为开源基座
Pi / pi-coding-agent [3][4][5][6] 模型适配、Agent 会话、工具调用、扩展与 Skills 核心候选，通过受控 SDK 适配器接入 不是多用户权限与发布系统；默认进程权限不能直接暴露给成员
Semantica [7][8] 语义处理、实体与关系、来源追踪、本体相关能力 Python worker 接入候选知识处理 不能把自动抽取结果直接当成已审核业务事实

Gitea [11] Git 仓库、分支保护与协作习惯 有源码协作需求时作为代码后端 文档、二进制模型和运行证据仍需自己的资产层
Plane [12] 工作项、周期、模块和视图 借鉴轻量任务与问题模型 不为少量任务引入另一套独立项目后台
OpenProject [13] 项目工作包与规划管理 借鉴阶段、交付与责任人组织方式 完整功能面超出两区工作台的范围
OpenMetadata [14] 元数据目录、关联和治理思路 借鉴变更影响分析与元数据可发现性 面向数据生态的整套部署不是本项目必需
MLflow [15] 运行记录、评估与模型注册 可选实验记录适配器 不覆盖文档、场景、任务和管理员资产发布的全部语义
lakeFS [16] 对象数据的版本化 海量数据集/场景文件时再评估 首版不引入数据湖分支与第二套版本事实源
DVC [17] 代码与数据版本协作 已使用 DVC 的仓库保留其工作方式 本系统只登记准确提交与对象摘要，不另造 DVC 兼容协议
WeKnora [18] 文档知识处理与检索入口 可选知识处理适配，已有部署优先利用 知识库条目不是具有审批状态的正式资产版本
Docling [19] 文档解析 封装为可替换解析 worker 解析文本必须保留源文件与页段定位，不能覆盖原文件
pgvector [20] 在 PostgreSQL 中保存和检索向量 搜索增强，不是权限或事实数据库 相似度不能证明兼容关系或测试通过
Oxigraph [21] RDF/SPARQL 实现 需要标准图查询时构建可重建副本 首版的权威数据仍在 PostgreSQL，避免双主写入

三种路线的比较

路线 能快速得到什么 主要代价 决定
整体改造 Backstage / Plane / 其他平台 现有导航和管理功能 两区界面改造深，资产版本和项目证据仍要重做 不作为默认
模块化单体 + Pi + 语义适配器 自己掌控核心流程，部署组件较少 要认真实现权限、版本和追踪关系 推荐
多微服务 + 图数据库 + 工作流平台全面组合 组织规模扩大后可独立扩容 运维、跨服务一致性和排错复杂 留作有测量依据的扩容路线

Pi 与 Semantica 的主仓库均标示 MIT 许可证；这不意味着其全部插件、模型、解析依赖和连接器都采用相同许可证。Plane 的仓库标示 AGPL-3.0。实际复制、修改、分发或以服务形式使用组件前，应按锁定版本进行许可证审查，并保留 NOTICE、SBOM 与第三方说明，不把“开源”当作无需约束。[3][7][12]

控件预算与常用操作

首页固定的主要操作只有发送消息；运行中变为停止。项目选择和导航是定位入口，不再放“智能分析、智能整理、智能生成、智能推荐”等一排重复按钮。每张对象卡保留一个主要动作，其余放进可发现的更多菜单。审批页可以同时提供“审核并发布”和“退回修改”，这是明确责任所必需的例外。

输入 @ 引用具体项目、资产版本或任务；引用显示名称和版本，不只有一个难辨识的 ID。自然语言可以说“把这个模型和它的测试整理成一个发布申请”。Agent 先生成提案，右侧呈现结构化差异，成员确认的是具体结果，不是一个模糊的“允许”。

也必须支持不经过 LLM 的上传、搜索、编辑属性、提交 Issue 和审核。不能让“给文件改名”都等待模型。创建、编辑表单只显示该类型必填项，进阶属性折叠；Agent 可以预填，用户可以直接修正。

状态与可访问性

加载、无结果、无权访问和连接失败必须使用不同提示。SSE 重连时显示“正在恢复运行记录”，不重复发起任务。刷新后保留项目、Session 和正在查看的资产版本。键盘可打开导航、切换工作区、定位输入框；焦点与状态不能只靠颜色表示。表格允许横向滚动但页面正文不横向溢出。

默认不展示大而密的知识图谱。先显示“直接依赖 2 项、被 3 个项目使用”的关系列表，点进去才展示局部图。复杂图也应提供同等内容的文字表格。

CHAPTER 05五个实际使用故事

先把最常发生的工作做顺，再扩展高级分析。

场景 A：把已有文件整理成可用资产

成员在“轨道传播验证”项目新建 Session，上传模型压缩包、接口说明和回归测试。系统完成隔离接收与摘要计算。Agent 建议把三份内容分别登记为模型、文档和测试库，并提出 documentedBy、validatedBy 关系。成员修正属性后保存到工作分支，提交 PR。管理员看到关系、文件和测试差异，审核通过后产生发布集。任何一步失败都不覆盖原文件。

场景 B：找到真正能复用的版本

成员问“给项目找一个支持 ECI、接口 v2、已有回归证据的传播模型”。检索先限定成员有权访问的正式版本，再做属性过滤、关系查询和文本召回。返回中分别说明“属性声明支持”“在某测试配置下验证过”“还缺什么证据”。用户选定后创建锁定版本的项目引用，不能只保存 latest。

场景 C：通过 Issue 修复共享资产

成员在已使用的版本上提 Issue，注明输入条件、预期和实际结果。维护人接收后建立修复任务和工作分支。Agent 可以整理复现材料和建议修改；测试用例先证明问题，再验证修复。PR 关联 Issue、任务和测试报告。新版本发布后，使用旧版本的项目收到通知，但不会被自动升级。

场景 D：管理员审核一个发布申请

右侧先显示“变更 3 项；接口未变；1 个下游项目需补测”。管理员可以查看本次文件、属性、关系及证据，退回不完整项。点击“审核并发布”时服务端再次检查身份、权限、最新基线和内容摘要。审批后的分支内容被修改，旧审批立即失效，不能靠之前的绿勾继续发布。

场景 E：完成项目并留下可复现交付包

项目负责人提出结题。系统检查需求覆盖、已验收设计、合并变更、准确版本的测试、遗留问题处置与交付物。Agent 起草结题说明，不能自行把未通过项改成通过。负责人和指定审批人确认后，形成项目基线、资产清单、测试证据与验收记录，保留后续维护责任人。

CHAPTER 06总体架构与模块边界

业务系统保存事实和规则，Agent 负责提出行动；文件库保存内容，语义组件提供可解释的检索线索。

推荐技术基线

层 建议 选择理由与约束
前端 React + TypeScript；组件、编辑器和关系视图库按需封装 用两区壳承载不同对象；重型编辑器延迟加载；不默认整套管理后台模板
API TypeScript + Fastify 的模块化单体 与 Pi 适配器共享契约；领域模块独立测试；已有成熟后端可保留，不为统一语言推翻现有代码
数据库 PostgreSQL；结构化表 + 有校验的 JSONB 权威业务数据集中事务；类型扩展不等于所有字段都塞 JSON
文件 BlobStore 接口；首版团队隔离的本地内容寻址库，可接已有 S3 兼容存储 元数据与文件分离；禁止直接按用户传入路径访问磁盘
后台作业 PostgreSQL jobs + outbox；worker 单独进程 首版无需 Redis/Kafka/Temporal；持久状态、租约与重试必须实现
Agent Pi SDK 适配器 + 业务工具网关 不向浏览器开放 Pi 裸 RPC 或任意 Shell
语义增强 独立 Python worker，封装 Semantica、文档解析、可选向量 故障不阻塞基础资产与版本管理
代码后端 本地受控 Git / 可选 Gitea 适配器 Git 对象和提交由成熟工具处理；业务发布以本系统为准

领域模块

身份与权限管理用户、团队、项目成员和授权策略。资产目录与本体管理类型、修订、属性、关系和来源。变更与发布管理分支、PR、审核、发布集、撤回。项目与任务管理需求、阶段门和交付。Agent Runtime管理运行上下文、工具调用、预算与恢复。检索与索引维护可重建派生数据。审计与运维管理事件、备份与诊断。

模块只通过明确的服务接口写入对方数据。Agent worker 不直接操作业务表；语义 worker 返回候选结果；索引器消费 outbox。禁止“前端直接连数据库”“每个模型插件自己修改版本状态”“某个 MCP 服务器拿管理员数据库密码”。

服务进程拆开是为了隔离故障与执行权限，不意味着需要把业务拆成分布式微服务。初期可在一台机器运行，依赖故障和网络超时仍按真实故障处理。

新增“仿真场景”类型时，先登记类型版本，再指定属性 schema、默认分类、允许关系与验证器。预览器、索引器和执行器通过扩展点注册；没有扩展时仍能作为文件资产查看、下载和版本管理。新增类别一般不需要改数据库表结构；新增跨对象强约束可能需要新增领域规则或迁移，这一点不能假装靠 JSON 自动完成。

关系定义表

关系 方向及典型对象 约束 如何确认
partOf 对象 → 项目 / 集合 用于组成关系时禁环；不自动授权 人工归属或受控导入

“被谁依赖”由 dependsOn 的反向查询得到，不由用户再维护一条可能矛盾的反向关系。是否允许环、是否对称、是否唯一，由关系类型定义决定；不能对所有边一概禁环，也不能让所有边都无限自由。

关系记录的必要字段

至少包括 team_id、稳定关系 ID、关系类型版本、源对象、源修订（适用时）、目标对象、目标修订（适用时）、适用条件、有效时间、来源类型、证据定位、提出者、确认者、状态与撤回原因。声明来自 LLM 时，还记录模型与提取规则版本，但模型的自评分不是校准后的置信概率。

业务强关系通过外键、领域约束和 PR 固化；语义候选单独保存为 proposal。候选不能混进正式依赖和结题检查。UI 使用“建议关联”“已确认”“已撤回”等文字标记，不只换一种线条颜色。

属性关联例子：模型的 output_schema 引用独立的接口 schema 资产修订；引擎的 accepted_schema 引用它支持的 schema 版本。系统比较的是版本化契约，不是两个自由文本都写了“state”。单位转换由受控映射执行，并在结果中记录转换版本。

可变与不可变边界

索引、租户与查询

高频筛选字段如 team_id、project_id、类型、状态、时间、资产 ID、修订 ID 建组合 B-tree 索引。对确需查询的 JSON 属性建立受控表达式索引或生成列；不要给全部自由字段铺满索引。关系表至少提供正向和反向邻接索引，图查询设置深度、节点数和执行时间上限。

服务端从真实登录会话建立租户上下文，不能信任用户请求体中的 team_id。数据库应用角色不应是表 owner、superuser 或 BYPASSRLS；对必要表启用并强制 RLS，后台作业使用独立受限角色。PostgreSQL 对 owner 与绕过角色有例外，不能只写一句“开了 RLS 就安全”。连接池中使用事务局部上下文，事务结束清理，测试连接复用是否串租户。[24]

类型扩展流程

管理员从已有类型复制定义，增加字段和规则，建立本体变更 PR。系统对样本与存量数据进行校验预演，给出“仍符合、可自动迁移、需人工补齐”的清单。审核后发布新定义；新修订使用新版本，旧修订仍按原定义解释。不能把历史 typeRef 偷偷改成最新定义。

属性改名不是简单删旧加新。迁移计划记录旧字段、新字段、单位转换、默认值来源与是否可逆；没有足够信息时禁止自动补造。新增必填字段对旧修订不追溯伪造，对新修订生效。关系规则变化同样需要影响分析。

本体治理的最低要求

命名空间防止同名碰撞；固定版本避免解释漂移；定义验证器与执行插件分开审批；关系候选先人工确认；导出 JSON-LD / RDF 时保留原始 ID 与来源。跨团队导入先做命名空间映射和 ID 对照，不能按资产名称直接覆盖。

可对模型定义“至少有一个接口描述”的形状约束，但“已验证”还必须由业务规则检查相应测试与证据是否有效。验证引擎不应把 status: verified 这一字段本身当作证明。

CHAPTER 12版本管理：给所有资产一套共同的语义

Git 管代码内容；本产品管理资产修订、变更审查和团队发布。两者关联，但不是同一个东西。

几个名称的准确含义

名称 定义 举例
Revision 某资产一次不可变内容快照 rev-model-42
Branch 一个项目中可持续修改的工作分支 feature/new-model-interface
Feature 变更意图或工作项，不是额外版本格式 支持新的接口协议
PR / ChangeRequest 将分支中的一组资产修改提交审查 CR-18，同时修改模型、文档和测试
ReleaseSet 一次被批准发布的原子资产集合 REL-12，包含 3 个准确修订

Version label 面向人的不可重复标签 model-a@1.2.0
Baseline 项目在某个交付节点使用的固定集合 验收基线 BL-3

Session 的分叉只是对话分支，不能自动等同于 Git 分支或资产工作分支。一个 Session 可以讨论多个 PR，一个 PR 也可以跨多个 Session 形成；关系要显式记录。

轻量分支的实现

分支属于项目，记录创建者、名称、权限、基线和状态。branch_entries 仅保存被修改资产的 base_revision_id 与 head_revision_id；未修改内容通过基线解析，避免每建分支就复制所有文件。每次保存生成不可变修订，只移动该分支头。被删除资产在分支中表现为删除提案，不直接删除全局资产。

首版将受保护的 main 作为当前正式发布内容的视图：stable 发布更新对应正式指针，preview 发布只更新 preview 指针。main 不承担未审核草稿的临时存放功能。

分支可以让受邀成员协作。成员看到这个草稿，不意味着它已经成为团队发布版本。向更多成员发布可安装、可调用的 preview 包，必须经过管理员审核，并设置可见人群和过期时间。任何发布通道都没有“临时版免审核”的捷径。

差异与合并策略

文本按三方差异比较；JSON 属性按 schema 知道类型后逐字段比较；关系按稳定键比较新增、删除与约束变化。两个分支同时改动同一个二进制文件时，展示冲突并由人选择或重新上传，不让 LLM 生成一个未经验证的“合并后模型”。

Agent 可写合并建议，不能掩盖冲突。自动合并后得到的是新候选内容，需重新执行相应检查。PR 目标基线已经移动时返回冲突，让用户重新预览，不能在管理员不知情时自动重放后发布。

CHAPTER 13管理员审核、正式发布与撤回

审批的对象是一份固定的变更和证据包，不是“以后这个分支怎么改都允许”。

PR 状态与发布边界

工作分支持续产生修订。PR 从 draft 进入 open，检查通过后进入 awaiting_review；管理员可以退回 changes_requested 或执行“审核并发布”。首版采用一次明确的人类动作完成审批和发布，避免给小团队增加两套重复表单。

在后台，这个动作仍分为准备、验证和事务提交。所有文件先完成持久化与可读验证，发布前准备好不可变审核快照。管理员可以浏览它；只有本人在真实登录状态下确认，才创建 approval 记录。服务端校验成功后将 PR 标记 merged，创建正式发布集并更新对应通道指针。检查未通过的 PR 不能直接调用接口绕过界面。

审核摘要必须包含什么

candidate_digest = H(canonical(
  asset revisions + full artifact digests + controlled properties/relations
  + target/base heads + ontology/type versions + required test plan
))
review_digest = H(canonical(
  candidate_digest + evidence digests + release notes
  + policy version + channel + permitted audience
))

规范化规则固定，不能直接 hash 一个字段顺序不稳定的 JSON 字符串。摘要只证明记录对应关系，不能替代真实身份验证，也不能证明测试结论正确。

对影响审核的内容、目标基线、证据、策略、本体或发布人群进行修改，会使旧审核失效。普通未纳入审批的讨论评论不必让整份审核失效，二者需在契约中区分。

发布事务与并发

展开：发布提交的服务端步骤
  1. 校验当前人类主体仍是授权审批人，PR 作者与审批人满足分离策略；获取请求幂等键。
  2. 按资产 ID 固定顺序锁定涉及的通道头和 PR，重新读取基线与政策，重算审核摘要。
  3. 检查所有制品可读、依赖可解析、检查结果匹配候选内容，确认没有未解决的冲突。
  4. 在同一 PostgreSQL 事务写入 approval、release_set/items、通道头、PR 状态、审计和 outbox；任何不满足条件则全部回滚。
  5. 提交后异步更新索引与通知。索引失败不撤销已完成事务，界面显示索引进度并通过权威库读取发布记录。

需要区分“发布事务原子完成”和“跨数据库、对象存储、外部 Git 完全原子”。本系统不承诺后者。文件和 Git 内容在准备阶段先确认持久存在；Git 分支镜像、通知和索引在提交后通过 outbox 重试与对账。官方发布记录始终引用不可变制品，而不是依赖一个可能移动的外部分支名。

审批职责与例外

默认不允许自己审批自己的 PR。团队至少配置一个备份审批人。确实只有一个管理员时，必须由团队事先启用“单人管理例外”，进行二次确认、填写理由并在发布记录中显著标注；Agent 无权启用或使用例外。不能为了方便把所有成员提升为管理员。

版本说明至少写明修改动机、关联问题/任务、变更内容、兼容影响、测试范围、迁移要求和回退限制。新接口破坏兼容时，版本标签与说明要一致；自动生成说明只是一份草稿。

撤回发布保留版本和证据，标记不建议继续使用并通知使用者。回退通过新的受审查事件把通道指向先前批准的准确修订；不会抹去后来版本，也不会自动逆转数据库迁移和外部系统副作用。

CHAPTER 14Git、二进制文件与大文件的处理

文件内容和业务版本分开管理。下载某份文件，必须能证明它属于用户有权访问的那个修订。

内容寻址库

文件接收采用临时对象、流式写入、大小限制、摘要计算、隔离扫描和格式识别。接收成功后转入不可变内容库，元数据只保存对象键、摘要、媒体类型和大小。对象键由服务端生成，不能直接采用用户文件名作为磁盘路径。

默认仅在团队内去重，不提供“这个摘要是否已经存在”的跨团队探测接口。压缩包限制展开大小、条目数和路径，拒绝路径穿越、符号链接越界和压缩炸弹。脚本、宏、HTML 与模型二进制一律不因预览或解析而在业务进程中执行。HTML 预览需消毒或隔离 iframe，并移除活动脚本。

原始 DOCX/PDF 等文件保持原样；抽取文本和缩略图是派生产物。历史预览定位依赖原始摘要与解析器版本，不能拿新版解析文本冒充旧版内容。可执行包的发布内容还需包括平台、构建参数、依赖锁定与制品摘要。

外部 Git 适配

代码资产记录仓库身份、准确 commit、可选 tree/path、构建产物摘要。Gitea 或已有 GitHub/Git 服务通过适配器提供拉取、提交映射、检查结果与回调；首版不重写 Git 服务。保护分支的思想可借鉴 Gitea，但具体版本支持的策略要在实施时测试。[11]

外部 PR 的通过不自动等于业务资产发布通过。回调要验证签名、事件 ID 与仓库范围，重复回调幂等处理；漏回调可通过定期对账恢复。外部仓库不可达时，已经保存并获准发布的内部制品可继续使用，无法取得的引用必须明确标记不可用。

删除、保留与迁移

存在项目基线、发布集、运行记录或审计引用的 blob 不得回收。先计算引用可达性，再执行保留期和冻结规则，最后由受控作业清理孤立对象。blob 从本地迁移到对象存储时逐个核对摘要并切换位置映射，不改变资产修订身份。

大数据版本需求明确后，可接入 DVC 或 lakeFS；它们的版本标识要映射到本系统稳定制品引用，避免同时维护两套互不解释的“最新版本”。[16][17]

登录与会话安全

首版采用成熟认证组件管理服务器会话，浏览器使用设置 Secure、HttpOnly 和合适 SameSite 策略的 Cookie；改变状态的请求增加 CSRF 防护。登录、权限提升和密钥轮换时按规则更新或撤销会话；退出与成员移除要使服务端会话失效。管理员敏感动作要求近期重新验证身份，已有组织登录服务时通过受控 OIDC 适配，禁止自行发明认证协议。首次管理员通过一次性受控初始化建立，不提供公开默认管理员密码。[37]

资产可见性与项目访问

普通正式资产默认团队可读，不因维护项目不同而禁止复用。项目成员资格控制项目内部需求、任务、讨论和草稿，不应阻断团队公共资产。跨团队默认隔离；确需交换时使用经过审批的导出/导入包，不提供任意跨租户关系边。

正式版本可读不等于可执行。测试运行、下载敏感制品、调用有外部副作用的工具需要单独检查。审批人拥有审查所需内容的明确授权；审计管理权与密钥查看权分离。

Session 分享尤其容易泄露

默认 Session 归创建者和项目策略控制。分享对话不仅可能暴露附件链接，还可能暴露已经生成在答案里的私有内容。分享前必须核对所有引用来源和产出内容的许可范围；不能只隐藏链接就把全文开放。

首版建议两种清晰模式：项目共享 Session 从开始就只使用该项目受众可读的输入；个人 Session 转分享时经过来源检查，无法满足条件则创建可审查的脱敏摘要，而不是直接公开历史记录。撤销访问后重新执行检索与内容授权，旧缓存不得继续返回受限内容。

轻量协同细节

支持评论、@提及、关注对象、待办收件箱和发布通知。通知点击后仍重新检查权限，通知摘要不能泄露私有文件名或结论。多人修改属性采用乐观锁/ETag；冲突时显示对方修改与本地草稿，不静默覆盖。第一版不实现多人实时同字编辑，采用显式保存与合并。

CHAPTER 17Agent 的边界：会做事，也必须受规则约束

Agent 擅长从零散材料中整理出一份提案。它不应拥有修改所有表、执行任意命令和批准自身工作的权力。

默认只需要一个主 Agent

主 Agent 负责理解任务、检索上下文、安排步骤和调用业务工具。文档解析、依赖分析、测试调度尽量采用普通服务或确定性工具。确实需要第二视角时，可以启动只读评审 Agent，但它的意见是证据之一，不是管理员审批。

Pi 可作为模型与 Agent 能力的复用层。其官方文档明确说明默认进程权限不提供文件、网络和凭据的安全隔离，扩展也可能在宿主进程运行。因此，必须由本系统限制工具和执行环境，不能把 Pi 启动起来就认为有了多用户安全边界。[3][6]

只读检索与预览可以在授权范围内自动执行。草稿写入必须限定项目、分支和对象。资源消耗型任务如测试运行需要预算与受控执行配置。发布、本体变更、成员权限、插件启用、敏感导出属于人类审批动作，不提供给 Agent 一个可以直接调用成功的高权工具。

工具名可包括 asset.search、asset.getRevision、relation.query、proposal.create、branch.saveDraft、issue.create、task.proposeUpdate、test.requestRun。名称是本系统拟定契约；不能根据工具名猜测上游 SDK 的真实方法签名。

CHAPTER 18Pi 接入、上下文与持久运行

项目身份、权限、预算和运行状态由业务 Runtime 管；Pi 只收到这次任务被允许使用的上下文与工具。

适配器而不是裸 CLI 转发

建议实现自己的 AgentAdapter 接口，优先对接 Pi SDK。官方 SDK 提供会话与生命周期操作；具体签名及 Session 切换行为随版本而变，实施时必须按锁定版本写契约测试。不能把浏览器 WebSocket 直接连到任意文件系统上的 Pi RPC。[4]

// contextRefs、allowedTools、budget、modelConfigRef、runtimeVersion。

官方 SDK 的默认资源加载会发现项目和用户目录中的扩展、Skills 与上下文文件。生产模式应改成允许名单加载器：只加载管理员批准的固定摘要版本，不扫描用户上传资产中的 .pi/extensions、AGENTS.md 或任意祖先目录来获得可执行指令。Skills 的说明文本与可执行扩展分别管理。[4][5]

如果上游会话切换会替换运行时对象，事件订阅、工具注册和状态绑定必须随之重建并测试。不要把“本地 CLI 能续聊”当成“服务端多用户会话可以安全复用同一个对象”。

上下文由五部分组成

系统规则与工具契约；当前用户的有效权限和任务边界；项目目标、需求及当前基线；用户选中的资产准确版本；本次检索获得的证据。历史对话只是上下文的一部分，不能覆盖数据库里的正式状态。

压缩对话时保留任务目标、已确认决定、未解决问题、引用 ID/摘要和下一步，原事件仍留在数据库中。上下文引用显示在 Agent 区，成员可以取消不必要的输入。摘要不作为批准记录、测试结果或持久任务状态的唯一来源。

运行状态与恢复

运行状态建议为 queued → running → waiting_user / waiting_job → completed，另有 failed / cancelled / blocked / unknown_reconcile。数据库保存运行身份、上下文快照、模型配置版本、工具调用、预算使用量、检查点和最终结果。

作业以租约和心跳确定执行权。断线重连读取事件序号，不能重发整次任务。worker 崩溃后从可重放检查点恢复；非幂等外部操作如果无法判断是否已生效，进入 unknown_reconcile，先对账或人工确认，禁止盲目重试。

每个 tool invocation 使用稳定调用 ID 和幂等键；任务队列采用至少一次交付，业务操作实现幂等。不要宣称整个系统天然 exactly-once。SSE 使用可恢复的 Last-Event-ID，事件落库后再发送；token 流可以批量保存，但最终消息、工具决定和状态事件必须持久化。

预算与取消

Runtime 限制每次运行的 token、工具调用次数、并发作业、磁盘写入、网络目标、单作业执行时限和总费用。达到限制时保存进度并等待用户处置，不让模型自行提高上限。取消操作应传播到工具网关和子进程，并撤销未使用的临时能力，不只是前端停止显示文字。

CHAPTER 19Semantica 与检索：把建议关系变成可审查的证据

先有可查的权威目录，再加语义增强。语义服务关闭时，分类、精确版本、审批与项目管理必须照常工作。

Semantica 提供本体、图与来源处理方向的能力；本方案把它放在适配器后面，选用需要的模块，不将整个演示平台连同多个后端全部设为启动前提。上游可视化对象的修改也不应被误认为本系统已经完成持久化。[7][8]

从文件到关系候选

文件以准确修订进入解析队列，解析器生成带页码、章节、偏移或表格位置的片段。worker 从片段提取实体、属性和关系候选，通过受控词表和 schema 做第一轮校验。消歧只提出同一对象的可能匹配；冲突进入待审列表，不覆盖已确认字段。

候选返回业务服务后，关联原文件摘要、解析版本、提取模型/规则、来源定位及现有对象版本。成员可接受、修改、拒绝；正式资产技术关系随 PR 固化。没人确认的关联可以帮助探索，但不得影响可执行依赖、发布准入或结题判定。

我们的适配器契约

extract_candidates(revision_ref, parser_output_ref, ontology_bundle_ref)
  -> candidate_entities, candidate_relations, evidence_anchors, warnings

validate_candidates(candidate_batch_ref, constraint_bundle_ref)
  -> structural_errors, conflicts, unresolved_entities

build_search_projection(authorized_revision_refs, checkpoint)
  -> projection_checkpoint, indexed_count, failures

这些是本系统期望的输入输出，不是可直接调用的 Semantica 函数。适配器实现需要检查实际模块、额外依赖和错误语义。针对中文、多文件同名实体、单位、历史版本、冲突属性、缺失来源和解析失败编写固定测试集，不能只运行 README 示例。

查询分层

“找接口为 v2 的正式模型”先用结构化过滤；“这个模型会影响哪些项目”采用关系遍历；“有没有类似的接口说明”可用关键词与向量混合检索。模型把这些工具结果组织成答案，不自行编造 SQL 在全库执行。

权限过滤在内容进入模型前完成。首版可对小规模授权集合采用精确向量搜索，降低过滤与近似搜索结合导致漏召回的复杂度；规模扩大后再以测试结果决定索引和检索策略。pgvector 是相似度检索组件，不能替代对象授权。[20]

查询结果同时展示匹配原因、版本、来源定位、状态与缺失证据。严格区分三种结论：元数据声明满足；规则校验满足；已经在某条件下测试满足。不要把“描述里有相关词”写成“已经兼容”。

检索质量验收

建立团队实际问题集，包括精确查找、版本比较、下游影响、来源定位和无答案问题。分别测量正确对象召回、引用定位正确性、权限泄露、过时版本混入、无依据结论。样本量、评价者、模型配置和失败样例都应留档；不以一个总分掩盖越权样例。

第一版启用顺序

先完成 Pi 的受控业务工具与必要的文档/测试能力。开发时按需选择一个目标管理扩展和一个代码评审流程；不要同时装几个争抢续跑生命周期的 /goal 插件。MCP 只接实际需要的系统；不存在真实业务用途的连接先不启用。

写作辅助应作为非执行型 Skill 管理：规则可以建议调整表达，不能删除来源、改变事实或给自己增加工具权限。humanizer 的重点是具体自然的表达，i-have-adhd 的重点是行动优先与清楚分块；复杂设计仍需保留完整的技术约束。[33][34]

三种不同的“持续目标”

开发 Agent 的目标是构建此软件；产品内用户的目标是完成某个项目任务；发布审批是一个明确的人类行为。三者必须分开。即使开发使用 pi-goal-x，产品运行状态也要进自己的数据库；即使产品 Agent 持续工作，也不能把持续工作理解成持续拥有发布授权。

前端按钮、Agent 工具与批处理导入都走同一套领域规则，不能各自实现一份“类似的权限检查”。

主要 API

所有路由以 /api/v1 为前缀；ID 为稳定 ID。敏感接口从服务端登录会话和对象反查团队，不靠客户端指定团队来扩大权限。

统一响应与错误

成功响应包含对象 ID、版本/ETag、审计关联 ID。失败响应包含稳定错误码、可展示说明、是否可重试、必要的冲突细节和请求 ID。不可见对象避免通过错误信息泄露其存在。

409 STALE_HEAD / REVIEW_DIGEST_CHANGED 表示内容或基线已改变；422 SCHEMA_INVALID / UNRESOLVED_DEPENDENCY 表示数据约束不满足；403 ACTION_NOT_ALLOWED 表示权限拒绝；429 BUDGET_EXCEEDED 表示预算不足；503 DEPENDENCY_UNAVAILABLE 表示外部组件不可用。错误不能统一伪装为“请重试”。

事件与幂等

领域事件包括 AssetRevisionCreated、RelationProposed、ReviewPrepared、ReleasePublished、ReleaseWithdrawn、ProjectBindingPinned、TestRunCompleted、GateReviewed、RunBlocked。每条事件有团队、聚合对象、顺序号、操作者、发生时间、schema 版本与关联请求。

发布等关键写入同时写 outbox；投递者可重试，消费者按事件 ID 去重。幂等键限定在团队、主体和操作范围内，不能让不同人复用一个键读取到对方结果。同一键配不同请求体必须拒绝。

保护正式资产不能只靠 Prompt。数据、工具、运行环境和审批接口都要有独立的约束。

主要威胁与防护

执行隔离

Agent 调度服务本身不运行任意用户代码。测试和仿真执行器使用非 root 进程、只读基础镜像、限定工作目录、CPU/内存/输出限制和默认拒绝网络。执行网络确有需求时申请明确目标。具备 Docker 管理权限的专用 worker 也应与业务 API 隔离，不能把 socket 挂载到每个 Agent 沙箱。

生产环境不允许从会话继承宿主用户的 HOME、SSH 密钥、云账号和浏览器登录态。MCP 的工具说明或“只读”注解不能代替实际权限审查。自定义工具即使由扩展提供，也必须走统一网关。

审计与真实性

审计事件记录主体、操作、对象版本、结果、请求 ID 与必要理由，脱敏后保留。应用管理员不能通过普通 UI 删除审计；可设置独立追加写角色与定期签名导出。哈希链可以帮助发现部分篡改，但如果同一管理员掌握数据库、密钥与备份，不能声称绝对不可篡改。

测试证据必须包含真实运行记录和制品摘要。测试被跳过、依赖不可用、结果不确定都要区别于通过。模型生成的总结应引用原报告，报告失败时不得改写成“整体正常”。

CHAPTER 23部署、离线和运维

小团队首先需要一套能稳定启动、能备份、能恢复的系统。不是组件越多越专业。

起步部署与可选配置

基础 Compose 配置包含 Web/API、PostgreSQL、worker 和持久卷。Pi 运行器与 Python 语义 worker 可以共用代码仓库，但使用独立进程/镜像与权限。模型服务可以连接现有推理接口，硬件预算中单独计算，不能把 LLM 显存需求混进 Web 服务容量。

文件存储起步采用服务端 CAS，并保留切换到已有 S3 兼容存储的接口。已有 Gitea、知识库、实验平台时通过适配器接入；没有就不为展示界面而额外启动它们。首版不依赖 Kubernetes、Kafka 或独立图数据库。

配置 必需部分 可关闭部分
基础协作 登录、业务 API、数据库、文件库、版本/项目工作流 LLM、向量检索、语义提取均可临时关闭
Agent 协作 基础协作 + Pi 运行器 + 受控模型连接 多 Agent、MCP 外部连接
语义增强 Agent/基础协作 + 解析与 Semantica 适配 独立图数据库、外部知识平台
离线部署 镜像、包、模型/嵌入、文档、漏洞库快照全部准备 外网文档检索、在线插件安装

离线和 ARM64 检查

部署前记录 CPU 架构、系统版本、容器运行时、可用内存/磁盘、模型接口与网络策略。锁定 Node/Python、Pi、Semantica、解析器、数据库扩展及镜像摘要；对 ARM64 的镜像和 Python 二进制依赖实际验证，不用“纯 Python 项目”推断所有依赖都兼容。

离线包包含依赖缓存、锁文件、模型与 tokenizer 来源、嵌入模型、前端静态资源、管理员手册、SBOM 和扫描数据库日期。字体、图标和编辑器资源本地化。启动时不自动下载模型、不联网刷新版本、不向第三方发送团队会话或遥测，允许经管理员选择后启用受控遥测。

备份与恢复

数据库备份需覆盖业务数据、审核和运行状态；文件库覆盖发布与历史引用内容；配置与密钥采用分离保护。通过备份检查点记录数据库快照与制品引用集合，验证所需 blob 均可恢复。只有 SQL dump 但没有文件，不算完整备份。

恢复演练至少包括：恢复到新实例；检验摘要；打开旧项目基线；下载旧正式资产；恢复后拒绝继续使用失效会话与临时令牌；确认待执行外部动作不会重复触发。写入期恢复策略应明确 RPO/RTO 目标，不能只说“支持备份”。

容量与目标

初次压测建议使用 30 名成员、10 名并发交互用户、10,000 项资产身份、100,000 个修订与 500,000 条关系作为可调整测试夹具。目标可先设普通列表/详情 P95 不超过 1 秒，发布事务 P95 不超过 2 秒（不含提前执行的测试与上传），SSE 已产生事件在正常内网下约 1 秒内可见。这些是验收目标，尚未测试。

上传、解析、模型首 token、生成速度、全量索引各自计量，不合并为一个“系统响应时间”。文件大小、数据库缓存、索引、CPU 与模型资源都会影响结果；未满足目标时先拿查询计划与跟踪证据优化，再讨论拆服务。

CHAPTER 29最终设计检查与明确边界

这个方案的关键不是 Agent 能说多少，而是团队敢不敢复用它整理和发布出来的资产。

本设计覆盖用户指定的七类资产，并提供扩展类型；保留项目 → Session 的会话组织；界面以 Agent 区和工作区为主；正式和候选上线均需管理员审核；Issue、分支、PR 与变更说明贯穿资产更新；项目全流程通过准确版本与证据关联起来。

需要实现团队保持的几条底线是：不覆盖历史修订，不在已批准内容之后偷偷变更，不让最新版本自动污染旧项目，不用聊天摘要代替数据库状态，不让候选知识冒充已确认关系，不在未验证环境上声称支持。

尚需在实施中确认的外部条件包括已有仓库结构、实际团队规模、部署架构、可用模型接口、身份来源、具体资产格式、执行环境和各上游锁定版本。这些条件不会阻止按本方案建设核心能力，但会决定适配器、数据导入和性能验证的具体实现。

第一轮可演示交付应围绕同一个完整样例：成员登记模型、文档与测试，提出关系与修改，管理员审核并发布，另一个项目锁定使用，随后通过 Issue 修复并完成一次项目验收。所有页面、数据、工具与审批都使用同一条真实记录链。

2. 产品约束不得擅自简化

界面保持 Agent 区 + 工作区。项目与 Session 在可收起的导航抽屉里，层级必须是“项目 → Session”。不得做成十几个常驻菜单、三四列面板、满屏 KPI 和智能按钮。顶栏保留定位和状态；输入框主要动作是发送/停止；详细属性、关系和工具事件渐进展开。用户登录后直接使用，不需要手工填项目 ID 或 Bearer Token。

工作区必须能显示项目概况、资产详情、文档/制品预览、修订差异、Issue/PR、任务、测试证据和审批。允许按当前对象切换视图，不把全部模块同时摆出来。提供空状态、加载、失败、无权访问、断线恢复和窄屏布局。核心流程必须支持不依赖 LLM 的直接操作，不能所有事情都强制聊天。

必需管理文档、软件、仿真模型、仿真引擎、测试库、Agent 库、场景；至少额外验证一个新类型通过定义注册接入。类别是目录视图，不是七个互不关联的数据库。身份、修订、分类、类型、标签、关系、项目使用、发布状态和权限必须分清。

团队正式资产默认可被普通成员读取和复用。私人/项目工作草稿只给作者、受邀协作者和审批人。成员可以提 Issue、讨论和 PR，日常任务更新不必全部审批；任何正式资产变更或候选版向指定人群上线都必须经过真实管理员审核。没有“临时发布免审”通道。

项目必须能从需求受理、需求基线、设计、开发与集成、测试、验收发布走到结题，并管理任务、负责人、依赖、阻塞、里程碑、交付物和遗留问题。不能把它退化成只有状态列的通用 TODO 看板。

3. 技术基线与复用边界

优先采用模块化单体业务层、PostgreSQL、不可变文件内容库、持久作业和 outbox、Pi 适配器、独立的 Python 语义 worker。已有仓库存在合理技术栈时保持它，必要差异写 ADR，不因偏好重写。

前端可采用 React/TypeScript。Pi 优先通过受控 SDK 适配；业务服务管理授权、上下文、运行和审批，不向浏览器暴露裸 Pi RPC 或宿主 Shell。使用锁定版本对应的官方接口，先写契约测试；不得把自己设计的接口说成上游已有 API。

Semantica 用于候选实体/关系、来源和语义处理，放在可替换适配器后。它不能直接更新正式依赖、通道头、审批结果或业务权限。关闭语义服务不影响基础资产与版本流程。文档解析、向量索引、图查询是派生能力，不是第二套权威事实库。

文件通过 BlobStore 接口管理。起步可用团队隔离的本地内容寻址库，并能接已有对象存储。二进制文件不塞入数据库 JSON/base64；不把用户文件名直接作为存储路径。源码版本能力使用真实 Git 或已有 Gitea 接口，不重写 Git 协议。

不用为了显得完整就引入 Redis、Kafka、Temporal、Kubernetes、多图数据库或大型多 Agent 编排。扩容或新增依赖必须说明解决哪个已观察到的问题。插件、镜像、包与模型固定版本和来源，记录许可证与依赖；禁止生产运行时自动安装 latest。

4. 必须固化的数据与发布不变量

稳定资产身份和不可变修订分开。每次修订包含文件摘要、属性、类型/本体版本、受控关系和来源。应用角色不能 UPDATE/DELETE 已固定的修订。版本标签不能被悄悄指到另一份内容。

数据库核心字段关系化，长尾属性使用受 schema 校验的 JSONB。重要关系有方向、对象/修订外键、适用条件、证据、提出/确认主体。跨团队使用复合键约束，不能拿任意 UUID 代替实体完整性。新增类型走类型定义版本；本体演进做影响预演，保留旧解释，不能自动补造缺失字段。

项目使用资产必须锁定准确修订。发布新版本不能自动改变旧项目；升级通过明确提案更新引用。项目基线是固定交付清单。候选关系不能参与正式依赖、执行或结题判断；相似度和 LLM 自评分不能证明兼容或真实性。

工作分支保存基线和被修改资产的头，修订保持不可变。文本、JSON 属性、关系与二进制分别比较；二进制冲突显式处理，不能用未经校验的模型输出自动合并。Session 分支不等于 Git 分支或资产分支。

发布 PR 必须有动机、Issue/任务、变更说明、兼容影响、测试、迁移和回退限制。审核绑定准确的候选内容、文件/关系摘要、目标头、本体/类型版本、测试证据、政策版本、通道和受众。内容或相关条件变化使批准失效。

首版采用一个明确的人类“审核并发布”操作。服务端检查当前审批身份、作者分离、政策与摘要，在固定顺序锁和头比较后，将批准记录、发布集、通道头、PR 状态、审计、outbox 原子写入 PostgreSQL。外部 Git、文件、索引和通知不能伪称跨系统原子；制品提前持久化，后续同步通过幂等与对账恢复。

默认不得自行审批自己；单人管理员例外只能由人事先配置并留明显记录。Agent 永远不能通过 approved: true、自然语言同意或权限提升工具批准自身发布。

回退是新的受审查事件，保留全部历史并说明不能自动逆转的外部副作用。归档和撤回不删除旧项目需要的内容与证据。只有满足引用、保留期和冻结规则的孤立对象才能回收。

5. 真实 Agent、权限和恢复

实现统一业务工具网关。每次调用检查真实主体、团队、项目、对象、有效能力、预算和幂等键。读工具、草稿写工具、沙箱执行与人类高权操作分开。发布、权限改变、本体批准、敏感导出、执行插件启用不得作为 Agent 可自主成功调用的工具。

生产使用允许名单 ResourceLoader。不得自动执行上传内容中的 .pi/extensions，不得让恶意 AGENTS.md 或 Skills 获得宿主权限。扩展代码与普通说明分开审查，插件权限固定且版本化。

运行状态、工具事件、证据、检查点和预算写入数据库。浏览器通过可续接 SSE 获取事件，断线后从序号恢复，不重新触发任务。worker 使用租约、心跳与至少一次投递，副作用通过业务幂等控制。未知外部执行结果进入对账状态，不盲重试。

真实模型连接必须可配置并测试工具调用、取消与错误处理。适配不支持的模型应明确拒绝或按已测试方式降级，不能靠 mock 答复装作成功。秘密通过服务端配置或代理注入，不放进前端、Prompt、普通日志或导出包。

执行器非 root、限定目录、限制资源、默认禁止外网，不挂宿主 Docker socket。URL 导入、MCP 和回调防 SSRF；文件处理防路径穿越、压缩炸弹与活动内容。取消应传播到实际子任务并撤销临时能力。

Session 分享检查源内容和生成回答的受众范围，不能只隐藏附件链接。检索、关系遍历、向量结果、缓存、通知和下载都必须授权；撤权后不能继续使用旧缓存泄露内容。

6. 按 M0 至 M5 持续建设

M0：建立仓库和环境基线，完成依赖/能力盘点、ADR 与验收台账。先确定最薄真实链，不陷入无限调研。

M1：完成身份、团队、项目与 Session、两区工作台、文件接收、七类资产、类型属性和来源关系。至少两个真实用户完成登记与读取，重启后保留数据。

M2：完成分支、不可变修订、差异、Issue、PR、审核摘要、管理员发布、候选通道控制、回退和精确引用。覆盖并发、越权和失效审批。

M3：完成需求基线、设计、任务、测试定义/运行、追踪矩阵、阶段门与结题包。未验证的关键需求能阻止验收。修订变化会使不再匹配的测试证据失效。

M4：完成真实 Pi 接入、受控业务工具、上下文引用、持久事件、预算、取消、崩溃与重连恢复。完成真实 LLM 发起的资产整理与 Issue 处理样例，不能越权发布。

M5：完成真实 Semantica 适配与候选审查、来源检索、失效降级、离线配置、备份恢复、安全与性能验证、开发和管理员文档。确认所有必需出口条件，不能因 M1 演示成功就结束整个目标。

每阶段都维护一个可演示的真实使用链：成员登记模型/文档/测试，提出关系与 PR，管理员审核并发布，另一个项目锁定复用，再通过 Issue 迭代并完成项目验收。数据和审计必须贯穿，不使用互相无关的静态假页面拼接演示。

7. 执行循环与防止提前结束

每轮先读取当前计划、验收台账和交接，选择一个最重要且未阻塞的任务。明确预期行为和失败测试，做最小实现，运行针对性验证，再做集成与回归。修复发现的问题，保存证据，更新台账，然后继续下一项。

代码评审与行为测试分开。可使用独立只读评审上下文，但不能把同一模型反复说“没问题”当作证据。发现设计问题时记录事实、修正契约和测试，保持用户必需范围；不得通过删测试、弱化断言、关闭安全规则或删需求使状态变绿。

不要在完成页面壳、计划、脚手架、一个 CRUD、mock 模型演示、一个成功测试或一个里程碑后直接宣称整个目标完成。有未完成且可执行工作时继续，避免以“后续可完善”替代已要求内容。

持续不等于盲目无限循环。维护任务与失败计数、预算和无进展检测。连续几轮没有新的证据或同一错误反复出现时换验证路径、缩小复现场景或记录真实阻塞。不得为保持运行而制造无关功能、反复改文案或无意义重构。

需要真实模型凭据、外部账号、硬件或管理员决定时，明确记录缺少什么、尝试了什么、影响哪些验收项；继续所有独立的未阻塞任务。等到仅剩外部阻塞时进入 blocked 状态，不写 completed。没有工具支持续跑时留下可恢复交接，不声称自己在后台继续。

用户停止、预算耗尽、授权不足或高风险动作缺少确认时暂停对应工作，不能自行增加预算、权限或外部操作范围。不得擅自把代码或团队数据推送、发布、发送到外部服务。

9. 完成时交付什么

交付可启动代码、固定依赖、数据库迁移、初始化流程、真实演示样例、测试报告、安全与恢复记录、管理员使用说明、配置说明、备份/升级/回退手册、许可证清单及未解决 Issue。README 给出经过实际执行的命令，而非猜测启动方法。

完成声明说明实现了什么、如何复现、哪些测试通过、哪些未验证、有哪些限制、当前分支与工作区状态。未获得外部推送授权时只交付本地成果，不自动 push、merge 或发布。

输出文案保持具体、自然、方便扫描：先给当前结果与下一行动；按主题分块；状态与证据靠近结论；不堆宣传词，不写假进度，不把不确定性润色掉。借鉴 humanizer 和 i-have-adhd 的公开写作方法，但不引入关于用户健康的推断。

现在开始读取仓库和设计文件，建立真实基线。完成第一项可验证工作后继续下一项，直到全部必需验收条件得到证据，或只剩明确的外部阻塞。
